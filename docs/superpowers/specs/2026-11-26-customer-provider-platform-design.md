# 客户管理、客户登录与服务商入驻正式设计方案

日期：2026-11-26。状态：客户方向与服务商首期范围已获用户确认；总体方向已确认；2026-11-28 A1a/A1b已合并，A2获准实施，B–F仍待后续批准。
本文件记录总体设计；A1a按2026-11-28实施计划执行，仅在独立虚构库迁移，不启用外部功能或真实发送。

## 一、目标与已确认决定

个人客户与企业客户兼顾。第一阶段支持企业多联系人，由员工逐项授权业务访问；
企业自助邀请、企业管理员后置。先交付客户总览、负责人和下一步跟进，同时纳入客户登录完善。
供应商／服务商作为独立业务参与方纳入总体架构，不能当成员工，也不能因注册自动成为合格合作方。
成功标准：员工一分钟内说清客户需求、当前业务、负责人和下一步；外部用户只看到明确授权的数据。

## 二、现有基础与证据

- 客户邮箱验证、挑战与会话、人工关联咨询、撤销、报价和进展视图已存在，默认关闭：

- 咨询已有团队、负责人、下次跟进、只追加记录；咨询可转现有唯一服务单：

  `docs/provider-review-summary.md`、`docs/provider-options-summary.md`。
- 现有客户登录不等于完善的客户档案；现有服务商申请不等于已有外部服务商账户门户。
- 以上为代码与文档核对，不是本轮重新测试，也不证明真实邮件或生产环境已验收。

## 三、架构选择

方案A：只按咨询归档，开发最少，但难以组织重复客户、企业联系人和长期关系。
方案B：统一业务档案，客户与服务商分别授权，复用现有登录基础。推荐采用。
方案C：直接建设完整企业租户及供应商交易平台，覆盖面大，但引入组织管理、结算和订单系统，暂缓。
用户已认可方案B的客户侧方向，并确认服务商首期同时支持机构和个人服务者，先做申请与补资料门户，任务协作后置。

目标为员工后台、客户入口、服务商入口。外部登录身份可复用认证机制，业务身份与授权分开。
第一批不强行合并现有认证集合；任何身份抽取须保留旧账户ID、会话和授权兼容性，另批迁移验收。
同一邮箱只证明邮箱控制权，不证明个人归属、企业成员身份、合作资格或签约权限。
客户与服务商身份可兼有；切换入口不继承另一身份的数据权限。员工登录继续独立。

## 四、业务对象与关联

| 对象           | 内容与边界                                                                       |
| -------------- | -------------------------------------------------------------------------------- |
| 客户档案       | 类型为个人或企业；稳定编号、名称、语言、国家地区、团队、主负责人、来源与存档状态 |
| 联系人         | 联系方式及验证状态；企业可多个联系人；同一个人可联系多个企业，关系分别记录       |
| 联系人关系     | 记录联系人所属客户、职务、主要联系人标记、有效期和撤销原因；不是访问授权         |
| 业务关联       | 客户与既有咨询、服务单的显式关系；保留原始提交信息与历史，不直接搬移业务归属     |
| 外部登录身份   | 邮箱验证与会话；不承担客户、企业或服务商的业务状态                               |
| 业务访问授权   | 身份、具体业务、可查看／可确认报价能力、证据、授权人、时间、撤销记录             |
| 跟进事项       | 客户、关联业务、事项内容、负责人、截止时间、状态与处理记录                       |
| 服务商档案     | 复用现有providers及合作状态，按个人服务者或机构表达，不另建重复合作主档          |
| 服务商成员授权 | 已验证身份与具体服务商关联；可维护资料／查看申请／处理指定任务分别授权           |

个人业务与其代表企业的业务独立关联。姓名、邮箱、电话重复仅提示候选，不自动合并。
历史数据允许未归档；逐条人工确认。首期不做不可逆合并，误关联可撤销且保留审计。
联系人身份与各客户关系下的业务联系方式分开；一个企业下的修改不自动传播到另一企业。
跨团队只显示当前有权关系中的资料，不通过共享联系人暴露其他企业或个人记录。
A1不修改旧外部授权；存在活动旧授权时阻断CRM关联撤销。D阶段才按明确证据来源设计选择性回收。
具体集合名、索引、API签名在各阶段实施设计中锁定，不以本总体计划直接开始建表。

## 五、客户总览与责任机制

总览包含基本信息、联系人、主负责人、进行中咨询、报价、服务单、下一步事项及最近动态。
列表支持按客户类型、本人负责、团队、待分派、今日到期、逾期、进行中业务筛选。
总览只聚合当前有权访问的记录；计数、搜索、导出、时间线和通知同样过滤，不能泄露隐藏业务存在。
内部成本、审核原因与内部备注不进入外部接口。信息读失败显示无法读取，不能当零条或无业务。

客户主负责人负责长期维护；具体咨询／服务单负责人负责交付，互不自动覆盖。
更换客户负责人时展示未完成事项，由员工明确选择转交范围；只允许转交给具备相应团队权限的现职员工。
转交记录前后负责人、操作人、时间、原因；事务内重新检查权限与版本，失败整次回滚。
客户主负责人不自动获得跨团队业务权限。停职、撤权或离职的未完事项进入有权主管的待分派队列。
没有有效主负责人时显式展示待分派，不自动指给任意员工。

## 六、下一步跟进

一个客户可有多个事项，每项包含明确动作、负责人、截止时间和可选业务关联。
状态为待处理、已完成、已取消；逾期由截止时间推导，改期保留原截止与原因。
完成可同时创建下一步，也可填写无需继续的结果；不强制对已结束客户不断创建新事项。
客户总览突出最早到期项与剩余数量。持久时间用UTC，第一版员工显示沿用现有北京时间并明确标注。

既有nextFollowUp建立来源映射，同一咨询只维护一个对应主跟进事项，不保留两个可独立编辑的时间来源。
首次迁移仅为有效未结束咨询建立待核对事项，不杜撰过去完成记录；关闭、重开、改期均同步原流程。
不能合理映射的旧数据列入人工核对。今日待办使用稳定来源键去重，原有绩效口径须回归验证。
并发完成或重复提交只记一次；事项完成不自动宣告成交，也不自动推进服务单阶段。

## 七、客户登录完善

沿用邮箱验证，首次成功验证建立登录账户；未登录仍可咨询，不要求先注册。
首期只开放已确认的中英文入口，其余语言遵循现有SITE_LOCALES配置。

1. 登录体验：验证发送／重发／过期／失败／退出提示，统一对外回执避免泄露账户存在性。
2. 新账户空态：显示暂无已关联业务及联系工作人员路径，不按邮箱自动领取历史咨询。
3. 员工逐项授权：查看与确认报价分开；授予确认能力须记录身份及代表权限证据。
   查看授权按明确业务对象记录；咨询授权不自动扩展到后来新建的服务单。
   确认能力授予具体服务单，实际确认仍绑定当前可确认的报价版本并重新检查原报价规则；
   新业务默认无授权，新报价版本不继承旧版的已确认结果。
4. 兼容旧授权：现有customer-inquiry-links不能在迁移时被静默扩大；旧确认能力须逐条可解释映射，
   无法证明时保留查看并进入人工核对，不凭企业联系人身份补发确认权。
5. 撤销即时生效：每次读写重查会话、账户与授权；企业联系人离职撤销其对应授权，不影响其他联系人。
6. 账户维护：联系邮箱与登录邮箱分别处理；登录邮箱变更需验证新邮箱并重新核对业务授权，撤销旧会话，
   邮箱失联时由管理员按证据审核恢复，不通过知道旧邮箱接管账户。
7. 停用账户与会话撤销、隐私告知版本和必要的服务通知偏好；营销订阅同意独立管理。

保持现有十分钟挑战、最多五次验证、十五分钟每邮箱三次及全站一百次、七天会话等安全契约，
如需调整须单独说明并补测试。真实邮件、HTTPS、域名验证和实际收件另设开放门禁。
企业自助邀请、企业管理员、短信、社交登录、密码登录均不纳入第一阶段。

## 八、供应商／服务商入驻

推荐服务商同时覆盖机构和个人服务者。客户购买服务，服务商提供服务；双方共享认证基础但不共享业务权限。
第一阶段仍由员工逐个审核、关联联系人和授权，不建设服务商企业管理员。

入驻路径：公开申请 → 邮箱验证并认领本人申请 → 补资料 → 员工核实 → 记录签约 → 按业务需要授权门户能力。
注册成功只获得申请管理能力，不自动通过核实、签约、公开展示或接单。
既有申请领取必须有员工核验或一次性绑定凭证，邮箱相同、同域名均不自动认领历史申请。
凭证绑定具体申请、目标已验证身份、用途与有效期，单次消费且只存摘要；转发不替代邮箱验证，
重放与并发只能成功一次。确切有效期在E1实施设计固定并测试边界。
申请待审期间只看本人的申请和对外补资料要求，不返回内部审核意见、风险判断或其他申请。

最小门户包括申请状态、补资料要求、提交资料修订、合作联系人和支持渠道。
服务范围、城市、语言复用现有标准字段；机构资质按服务类别按需采集，不统一索要所有敏感证件。
服务商修改资料保存为待审核修订，不能直接覆盖已核实或已公开资料；审核失败保留原有效版本。
材料必须私有存储、鉴权下载、限制类型和大小；审核前按不可信文件处理，不挂入公开媒体目录。
联系邮箱变更需重新验证及员工确认，资质变化触发复核，不能由服务商自己改合作状态。

合作状态沿用applied、needs-info、verified、contracted、paused；关闭申请采用另行存档标记与原因，
不擅自重写现有状态含义。核实／签约／暂停仍由现有有权员工操作并记录原因。
公开展示继续单独审批；同意合作不等于同意公开联系方式。暂停后不自动恢复公开或已停项目。

后续协作门户才增加员工明确指派的任务。服务商仅看任务所需的最少客户资料，不看客户总览、
其他供应商、内部毛利或全单报价。客户联系方式默认不提供，需要时按具体任务授权。
任务指派不等于接受：由服务商明确接受／拒绝并填写安排；不做自动派单、自动预订或在线支付。
暂停合作后阻断新任务和业务操作；进行中任务移交员工处理，保留必要历史与补资料入口，
E阶段暂停用户只可看本人申请状态和提交指定补资料，不可改已核实／生效资料或操作合作业务；
账户被停用则所有外部访问撤销。F阶段再确认任务历史与移交的精确矩阵。

## 九、权限与业务不变量

| 用户             | 可做                                       | 不可自动获得                           |
| ---------------- | ------------------------------------------ | -------------------------------------- |
| 员工             | 按原角色、团队、负责人管理客户／申请／业务 | 跨团队数据、内部成本或审核例外         |
| 个人客户         | 查看明确关联业务；有确认授权时确认报价     | 同邮箱历史业务或同行人的业务           |
| 企业联系人       | 查看获授企业业务；按独立授权确认报价       | 企业全部业务、邀请成员和管理其他联系人 |
| 申请人           | 看本人申请、提交补充资料                   | 已核实资格、公开展示、客户资料和接单   |
| 合作服务商联系人 | 看获授档案和具体任务，按能力操作           | 员工权限、全量客户信息、其他服务商信息 |

授权、转交、确认、资料审核、停用与撤销在事务内重查身份及权限，并与审计同成败。
报价确认不是付款，记录签约不是电子签署，资料核实不作外部资质保证。
存档不等于删除；实际数据保留期限、隐私文本及材料保管责任在真实开放前由业务方确定。

## 十、范围、上线条件与待确认项

首期不做支付结算、供应商佣金、自动派单、评分排名、电子签约、企业管理员和客户自动合并。
只使用虚构本地数据开发验收；真实账号、费用、发送、公网文件接收和部署不在本次授权范围。
各阶段独立迁移、可恢复备份、权限测试和中文小结；不覆盖现有演示库或reset解决迁移。

用户已确认：机构与个人服务者均可申请，首期仅申请与补资料门户；任务协作后置，具体范围另行确认。
真实开放前还需确定服务类别所需资质、补资料处理时限、签约与对外承诺文案、数据保留规则。
这些条件不阻挡先实施已确认的客户后台阶段，但阻挡对应服务商门户开放。

## 十一、固定角色与操作权限矩阵（用户已确认）

首期固定员工角色沿用admin、manager、operations、editor、reviewer，不新增任意角色／字段规则设计器。
外部业务身份分为个人客户、企业联系人、服务商申请人／合作联系人；这些不是员工角色。
有效权限为现职或有效账户、角色能力、记录范围、显式授权、字段许可、当前状态的交集；默认拒绝。
员工既有additionalRoles继续按固定能力组合，但不能绕过团队、字段、禁止自审或状态限制。
内容编辑／内容审核角色本身不取得CRM权限；兼任运营／主管时仅按该固定业务角色取权。

字段级契约：未授权字段从响应中省略，不以隐藏组件代替过滤；不返回真实值或可推断的摘要。
请求出现受控字段（角色、团队、审核、成本、状态、授权范围等）须按入口白名单拒绝并保持事务无写入，

列表、详情、搜索、筛选选项、排序、数量、通知、SSR／水合数据、导出、历史版本及关系展开均遵守同一规则。
对拒绝操作返回一致错误，不通过响应差异确认隐藏客户／企业／申请是否存在。
