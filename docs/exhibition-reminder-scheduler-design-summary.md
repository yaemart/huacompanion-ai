# 受控本地展会提醒调度：设计小结

[正式设计](superpowers/specs/2026-11-27-exhibition-reminder-scheduler-design.md)基于已合并PR125，本轮仅设计，尚未实现或启动调度，未改.env或原数据库。

用户已确定：管理员指定“本届展会＋语言”清单，显式启动本地进程；会话到期、登出或撤权后停止。发生提交结果未知时，同一数据库所有后续自动调度都须受持久阻断，更换状态目录也不能绕过。只生成本地待发，保留审核、写锁和H真实试发门禁；真实发送留后批。

## 建议运行方式

- 采用现有Node/TypeScript原生前台进程，不自动随网站启动。私有清单建议1–20个范围、最多16KiB，启动后固定，不跟随下一届或扩大为所有展会。
- 立即检查一轮，一轮结束60秒后再检查，始终串行。空闲最长5秒后发起原生会话复查；本进程单条SQL/锁等待建议10秒超时。认证只使用已有有效管理员JWT，不自动登录/续期。
- 以数据库北京时间判断恰好开展前30/7天；漏日不补，暂停恢复只检查当前日期。同日后来确认的订阅可在下一轮进入。
- 每次沿原预检/应用服务；清单内资格失效时取消旧held并保留历史，已审核新修订重新预检。无变化轮次不写记录或审计；每个范围独立提交。

## 未决与恢复

生成前先可靠保存私有回执，再在原审计表留下持久未决标记。失败/未知停止整次调度，不自动换回执、新预检或重试。单实例锁仅防同时运行；数据库控制审计才决定是否有全局未决。

只读回执查询必须真正只读；现有apply在没有历史且封套仍有效时可能写入，因此不能拿它冒充查询。已提交回执仍显示原结果和“当前资格未检查”。查询不隐式解除阻断。

另设明确的管理员控制结束：停止原进程、取得单实例及原写锁，重新核对生成审计；已提交仅核实，未提交则作废旧运行/封套，均只追加控制审计，不生成或重试。为避免原账号撤权造成永久阻断，其他现职管理员也可带原因核实结束，但不能认领他人回执或替他人生成。旧进程后到的写入必须在原事务锁内被拒绝。

这里的全库阻断仅约束本功能的自动调度，不冻结审核、正常订阅/退订或其他业务。

## 验收与切分

独立可实施性检查已完成一次，仅提出跨目录阻断范围问题，用户已选同库持久阻断；其余默认值作为实施者提议随设计审阅。

预计两个顺序增量：先做只读回执核实及全库恢复门禁，再在合并后做调度循环；各PR业务源码增删默认≤400，实施计划先核算。前一增量不能宣称自动调度已完成。

实施后以独立随机虚构库验证真实多进程、会话失效、重启/换目录、控制标记与生成故障、两个锁顺序和旧进程延迟写入；旧邮件/活动/尝试/租约/预算不变，对外调用0。按项目要求完整检查、相关集成、构建、更新交接、提交推送草稿PR，不自动合并。

代价：电脑休眠或进程关闭不保证持续运行；会话过期需重新登录并显式启动；未知结果需管理员核实结束；本地私有证据须保留。无新依赖、调度数据表/迁移或必需环境变量的设计提议；原库未升级。现有排除原因分类及两个Unicode标题分隔符的轻微遗留保持另批。
