## 已确认的组合

采用 **Cloudflare Web Analytics + 华伴站内每日业务事件汇总**：前者供流量与性能参考，后者在阶段 4 只保存日期、页面、事件类型、合作方编号、次数。这样不新增需要维护的统计数据库，也不依赖匿名个人会话标识。自定义事件不会发送给 Cloudflare，不调用其未提供的事件 API。这个分工已随停止点A方案确认；业务事件由站内汇总承担，Cloudflare单独无法满足。

选 Umami 时，先另行确认是否接受其匿名会话机制及额外维护成本；严格维持当前数据范围，就需要先评估受控事件上报能否避免这些字段，而不能直接加入默认浏览器 tracker。本轮未评估或承诺已实现这一改造。两种方案均不采集邮箱、表单内容、国籍、行程日期、客户编号或包含这些信息的 URL。Cloudflare 仍会接收网络请求，不将“不做个人指纹”宣传为平台在网络层完全不处理 IP；部署时须检查应用、网关及平台日志是否可按任务要求关闭 IP 留存。

## 指标口径需要一起确认

在没有任何个人标识的每日计数表里，同一人点击三次会计三次，无法计算准确的“有效访客人数”或个人跨步骤漏斗。阶段 4 显示 **有效行为次数**，并分别显示已确认订阅数、咨询数和成交订单数；合作方访问显示访问次数，结算不能把它当作独立人数。此为所选方案的数据口径说明；阶段4再实施，当前没有统计代码。

阶段 5 的第一方 Cookie 只保存合作方编号、30 天到期，不能用于识别人。订阅、咨询、订单的业务记录沿用各自必要信息及权限，不能把其 ID 复制进匿名事件表。安全限流与业务统计分开，不拿限流客户端键做访客追踪。
