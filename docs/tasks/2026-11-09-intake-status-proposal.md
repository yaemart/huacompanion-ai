现状：咨询有六个处理状态、八个协调进度；另有服务单履约阶段。两项咨询字段目前独立保存，可能出现“已关闭／联系客户”等组合。报价发出与客户确认在服务单中另有受控操作，不能用编辑咨询状态替代。

建议保留两维并联动，避免合并丢失“整体业务结果”和“具体下一步”。“处理状态”用于列表与统计，“协调进度”说明当前正在做什么。服务单阶段仍独立，不增加员工权限，不把咨询改为“已成交”当作签约、收款或报价批准。

| 合并成一个状态                       | 只填一次                               | 要重定义原六状态统计口径，无法同时表达“已报价＋等待预约”等信息，不推荐 |

已批准的第一步规则（后续独立小 PR 实施）：

- 新建咨询仍是“新咨询／待受理”。不根据进度自动生成已报价或已成交，不改变现有报价／客户确认流程。
- 开放状态（新咨询、待补充、处理中、已报价、已成交）可按实际情况选择非关闭进度。两维非终态之间只提示含义，不强制一一映射。
- 在任一字段选择“已关闭”时，明确提示另一字段也会关闭，必须填写关闭原因；用户确认后，同一事务更新两字段并记操作者、前后值、原因和时间。取消则两者均不变。
- 从“已关闭”重新打开也必须明确操作、填原因；同时选择新的处理状态及协调进度。只改一字段造成矛盾的 API 请求拒绝，不能绕过界面。
- “已完成”仅表示协调事项完成，不自动把处理状态改为已成交；未成交的免费协调也能完成。界面显示“协调已完成，成交状态另行确认”。
- 既有记录不批量改值、不重写版本。发现旧关闭矛盾时标记“请核对状态”，保留原值；员工下次保存涉及状态的修改时按新规则修正，修改联系人等无关字段不阻断。
- 服务单阶段和报价动作本步均不回写咨询。若希望发出报价后自动变“已报价”、成交后自动变“已成交”，建议在 F 的二审与发出流程稳定后另行确认事件映射，不能现在提前绕开 F。
