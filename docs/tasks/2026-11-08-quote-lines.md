## 数据结构与权限

每个报价版本使用稳定`lineId`标识费用项。对客信息留在报价行；成本以“报价ID + lineId”关联独立私有记录，沿用现有主管/管理员成本权限，原始集合的通用CRUD继续关闭。

| 对客字段                   | 说明                                                                       |
| -------------------------- | -------------------------------------------------------------------------- |
| lineId、费用名、数量、单价 | 保留现有最小金额单位与总价计算，行ID不能用费用名代替                       |
| 经营模式                   | 合作对接 / 华伴统筹，由服务方决定默认值并按下述规则校验                    |
| 实际服务方                 | 优先从已核实/已签约名单选择；保留手填例外并在审核界面标记                  |
| 签约方、收款方             | 每项明确客户可见名称，保留主体来源和人工修改记录                           |
| 模式说明、代收说明         | 使用后台可配置的说明，随已发出报价版本保留当时文字，后改配置不能改写旧报价 |

服务商使用现有记录ID关联，同时在报价正式版本保留当时显示名称；服务商后来更名不改变历史报价。公司主体使用后台配置的公司主体名称，不虚构法定名称。手填项保留明确来源标记，不自动加入“已核实”名单，也不扩展供应商管理权限。

成本明确为“本项成本合计”，与报价同币种、以分等现有最小单位存储，避免数量重复相乘。未知为空值，不是0。客户和普通运营不得取得分项成本、成本合计、毛利或毛利率。

不能只把成本塞入`lines` JSON然后在前端隐藏：当前`publicQuote`将整个`lines`传给客户，普通员工读取也只删除顶层`internalCostMinor`。实施必须做逐行公开白名单、主管专用成本查询及导出/邮件/日志/AI边界回归。对客代收说明可见，内部原因、确认记录和成本不进入客户投影。

## 1. 默认经营模式与主体（用户明确规则）

| 服务方                               | 默认经营模式 | 签约方默认   | 收款方默认   | 可否修改                                 |
| ------------------------------------ | ------------ | ------------ | ------------ | ---------------------------------------- |
| 华伴自营，如协调服务费、华伴员工陪同 | 华伴统筹     | 华伴         | 华伴         | 不可修改，锁定                           |
| 外部服务商，从已核实/已签约名单选择  | 合作对接     | 该服务商     | 该服务商     | 可修改，遵守代收和主体差异规则           |
| 手填服务方，例外情况                 | 合作对接     | 手填的服务方 | 手填的服务方 | 可修改，遵守相同规则；审核界面标出“手填” |

“华伴”取自后台公司主体名称。未配置时可以保存非代收草稿，不能提交审核。报价模板中的模式与主体只是初始值，不能覆盖本表的锁定和校验规则。

服务方选择器优先展示符合状态的名单，停用/未核实项不得作为新选项；保存及提交时服务端重新检查，不接受伪造ID或前端绕过。现有服务商状态如何对应“已核实/已签约”在实现时明确映射，不借本任务重构合作状态。手填通过显式例外入口使用，不把随意输入伪装成名单选择。

默认值在新建或明确更换服务方时应用，切换前提示将重算哪些主体和模式；手工修改、模板内容仍须服从规则，不静默改写已发出版本。主体识别不能只依赖显示名称相同，需保留华伴/服务商/手填的来源及关联，避免改名绕过锁定或代收校验。

## 2. 签约方与收款方

默认两者相同。签约方不等于收款方时必须填写原因，并在报价审核时由审核人单独确认；缺原因不能保存该变更，未确认不能批准或发出。审核权限、禁止自审及管理员有原因的例外沿用下述边界。

若同时属于代收，保留主体差异原因与逐项代收确认，不能用一个未指明对象的全单勾选替代。改变服务方、经营模式、签约方、收款方或相关原因后，对应旧确认失效，须重新审核当前修订。

## 3. 华伴代收第三方款项（用户明确规则）

定义：服务方不是华伴自营，但收款方是华伴。包括外部服务商费用项改为“华伴统筹”，或者手动将收款方改为华伴；模式与收款主体必须一致，不能保留互相矛盾的对客说明来绕过代收检查。

### 总开关与起草

- 后台增加“允许华伴代收第三方款项”，默认关闭，只有管理员可以开启。用户将在律师确认业务边界后再开启；开发和本地测试结束后保持关闭。
- 开关关闭时，代收费用项不能保存，提示原文：“当前未开放代收，请改为合作对接，或联系管理员”。不得仅禁用按钮，服务端同样拒绝。
- 开关开启后，起草人修改收款方时必须选择代收原因：客户要求统一付款 / 服务商不能直接收外币 / 其他，并填写说明。模式变更导致代收时同样校验，不能绕过起草记录。

### 逐项审核与发出

1. 每个代收费用项在审核界面显示独立提醒卡片，审核人必须逐项勾选原文：“已确认本项由华伴代收，并已与服务商约定转付”，否则不能批准。
2. 审核人须有报价审核权限且不是报价起草人；管理员自审例外须写明原因。服务端核对角色、当前修订及费用项，不信任前端自报的审核人或勾选结果。
3. 在报价审核时、发出前完成确认。已发出后如更改代收，必须另存新版本并重新审核，不原地改合同事实。
4. 设置、修改、确认均写审计：谁、什么时间、哪个报价版本和费用项、原因；批准记录须绑定精确修订，重试不得重复确认其他版本。
5. 开关关闭后不得继续保存或发出新的代收报价，也不能沿用先前批准绕过；已经发出的历史报价保持原文和审计，不自动重写或删除。

客户版对代收项目显示固定说明，默认原文：“本项由华伴统一收款后支付给服务方”。后台可配置文字；发出时冻结为该报价版本的公开说明。此功能记录责任和确认，不实现收款、转付或支付账户接入。

## 4. 客户版经营模式说明（用户提供的默认原文）

- 合作对接：“本项由上述服务方直接为您提供服务并收款，华伴负责协调沟通。”
- 华伴统筹：“本项由华伴负责安排并收款。”

后台可以修改默认文字。普通合作对接采用第一条；华伴自营及统筹采用第二条。存在代收或签约/收款差异时，对客说明须与实际主体一致：代收项使用代收专用说明，不能同时显示“服务方直接收款”的相反陈述。其他主体差异仍须逐项清楚展示三方，不因通用说明隐藏实际收款方。

## 5. 提交前校验与审核范围

保存草稿允许未完成的普通字段，但不能保存违反自营锁定、关闭代收、代收缺原因/说明或主体差异缺原因的变更。提交审核及发出前由服务端重新检查：

- 后台公司主体已配置；各费用项模式、服务方、签约方、收款方齐全，金额与数量满足既有校验。
- 自营模式和主体锁定；名单选项及手填标记有效；模板不绕过主体规则。
- 代收开关、逐项原因/说明齐全，签约/收款不一致的原因齐全。
- 所有报价（含人工报价）发出前，整单当前修订须经有权限的第二人审核；差异项和代收项另须逐项确认。起草人不得借另一个费用项、旧版本或AI/人工来源差异绕过自审。
- 旧未发出稿已经另存新格式并补齐主体；已发出及确认版本仍不可原地修改。

### 用户新增的明确业务规则：所有报价发出前第二人审核

用户于2026-11-08明确决定：所有报价，包括普通人工报价、AI报价及不含代收的报价，发出前都必须经第二人审核。审核人具有现有报价审核权限，禁止起草人自审；管理员自审例外仍必须写明原因。与报价分项同一实施阶段交付，不再保留“人工报价无需二审”的旧建议。

这是相对当前“仅AI来源强制主管审核”的明确业务变更，须同时覆盖服务端所有发出入口及后台交互，不能只隐藏发出按钮。批准绑定精确报价修订和当前内容；批准后若改动金额、费用项、主体、模式、说明等对客合同内容，必须使旧批准失效并重新审核。另存新版本不得继承旧版批准；已发出历史版本不追溯重审或改写。

没有有效第二人批准的旧未发出稿，必须按新规则审核后才能发出；管理员例外按既有理由和审计规则执行，不新增普通员工例外。代收及主体差异的逐项确认仍独立保留，整单二审不能代替这些确认。

## 6. 主管毛利视图（实现建议，供本文审阅）

在报价主管视图按费用项展示对客小计、本项成本合计、毛利、毛利率及合计；只允许现有主管/管理员成本权限访问，并遵守服务单数据范围，不扩展其他员工权限。

建议计算：本项毛利 = 本项对客小计 − 本项成本合计；毛利率 = 毛利 / 对客小计。对客小计为0时毛利率显示“—”；允许真实负毛利，不截为0。任一成本未知时该项显示“待补成本”，整单毛利注明不完整，不用0冒充真实成本。金额按原币种最小单位运算，比例仅用于显示。

历史总成本未分摊时单独显示原总成本及“尚未分摊”，不得与新分项成本重复相加，也不虚构每项毛利。此视图不是净利润或已回款统计，不新增税费、收款或结算模块。客户页、普通员工API、公开下载及邮件中均不得出现成本或毛利字段。

## 老报价迁移与安全措施

1. 数据库与图片配套备份，在独立克隆清点全部报价版本、状态、币种、金额、原`lines`形状、顶层成本和服务单关联。
2. 只增加可空结构/格式版本及私有成本记录，保留旧`lines`、旧总成本、ID、修订、总额、状态、发出/确认时间。历史新增字段显示“历史版本未记录”，不猜经营模式或责任主体。
3. 行对应关系使用报价ID、原序号和行指纹，不只按名称；已发出/确认历史不改写。映射重复运行幂等，失败整组事务回滚。
4. 旧总成本原值完整保留，不均摊、不塞第一项、不当作分项0。主管人工分摊只写新版本并审计。
5. 旧未发出稿保留，发出前“以新格式另存一版”并补齐主体与相应审核；旧已发出/确认稿保持原合同事实。新默认值不追溯填入历史或自动启用代收。
6. 核验原字段指纹、总额、关联、确认幂等、替换版本、过期拒绝及角色边界。仅无损条件下允许回退，否则保留新数据，拒绝删除新成本记录完成down。

## 实施验收

- 所有来源报价发出前二审：人工/AI/普通/代收均覆盖；未审发出拒绝、无审核权拒绝、起草人自审拒绝、管理员无例外原因拒绝、有原因例外留审计、改稿/新版本旧批准失效。
- 默认值、自营锁定、公司主体缺失、模板绕过拒绝；名单状态与伪造ID拒绝、手填审核标记。
- 关闭代收时保存拒绝；开启后原因/说明必填；非审核人、起草人自审、管理员无例外原因均拒绝；逐项确认不能跨项、跨修订复用。
- 签约/收款不同的原因和独立确认；变更后旧确认失效；已发出更改必须新版本重审。
- 对客三方及模式/代收说明与该版本一致；后台改配置不改旧版本；所有对外及低权限出口成本和毛利不泄露。
- 主管毛利覆盖空成本、0对客金额、负毛利、未分摊历史总成本，避免重复计成本。
- 迁移克隆验证、权限/报价/客户数据单元及集成回归、桌面和手机浏览器验收。真实新同事独立完成“咨询转报价并提交审核”，用时与卡点附实现PR，开发自测不冒充。
- 每次提交前运行`npm run check`及相关集成，lint警告不增加；截图放PR附件，实际验证写`docs/progress.md`。

本次文档PR合并后仍先做政策P0。代收开关默认关闭不变，其真实启用须用户在律师确认后决定；共用事实已另获批准，须先于报价实施；本规则不代表批准购买、部署、付款或实际代收。
