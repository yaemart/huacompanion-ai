# 停止点 C：政策更新群发方案比较

日期：2026-11-19。状态：**待用户选择；未实施**。从 PR81 合并后的 `main`（`912b154d3f510fff6d3112b314a8fa360104c7fa`）准备。本文件及摘要均为方案，合并文档不等于批准群发或真实发送。

## 1. 本次要决定什么

按[原任务说明](../traffic-entry-task.md)停止点 C 比较两条路线：A 同步已确认的订阅者到外部邮件工具；B 在华伴后台按主题受控发送，需要主管权限、先测试、防重复和限速。**建议本阶段选 B，先在本地模拟实现**，原因是运营正在集中亲测华伴后台，B 更便于统一权限、发布版本、退订和审计。它的开发及长期维护工作更多，不是现成群发工具。

如果最看重现成的邮件编辑器、排期和营销报表，并接受管理员到另一个后台操作，A 更合适。A 以原任务书举例的 Resend 为具体比较对象，不另外引入 Mailchimp/Brevo 等服务。当前 Resend 文档已将旧 Audiences 改为 Contacts、Segments、Topics；后续不能照旧 Audience 接口直接开工。 [官方联系人模型](https://resend.com/docs/dashboard/contacts/introduction)

两案首批均仅做“政策更新”，分别准备中英文内容；单场展会提醒、采购指南的批量发送及自动定时触发留给后续对应任务。政策发布不会自动触发外发。新增依赖、账户购买、部署、真实测试发送、真实群发均不在本次授权内。

## 2. 当前代码的能力与缺口

- 已有按邮箱＋主题的双重确认、同意版本、退订、管理员名单/CSV与审计；普通主管当前不能读订阅邮箱或导出名单。
- `subscription-mail.ts` 只消费单封确认与用户所选政策资料任务；`workflow/mail.ts` 通过 Resend `/emails` 发件，现有 worker 有重试、唯一键、同邮箱锁和限额。**这不是群发任务模型，不能把筛选出的邮箱直接循环塞入旧队列。**
- 原确认/资料发送跨主题按邮箱间隔 15 分钟、滚动 24 小时最多 5 次尝试；单次任务最多 5 次尝试，重试受 23 小时窗口限制。新群发不得放宽这些约束。
- 尚无外部联系人同步、群发活动/逐人任务、投递回执接收、营销拒发名单或供应商账户验证。现有的“模拟发送成功”不等于真实投递成功。

## 3. 两案比较

| 比较项       | A：同步到 Resend Broadcasts                                               | B：华伴后台受控群发（建议）                                       |
| ------------ | ------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 员工操作     | 管理员在 Resend 写邮件、选分组、发测试和正式发送；华伴保留申请与审计      | 获单独授权的主管在华伴选已发布政策、预览、模拟/测试、手动确认发送 |
| 邮件内容     | 外部有现成无代码编辑器、模板、排期                                        | 首批固定中英文模板引用已发布政策，不另建自由排版编辑器            |
| 名单         | 华伴保留同意原始记录，Resend 额外保存邮箱、语言分组、主题和必要的同步标识 | 不同步营销联系人库；按华伴当前订阅状态生成逐人任务                |
| 权限         | 外部权限是另一套，不能假称自动继承华伴团队权限                            | 可在华伴逐次检查主管授权；现有管理员名单/CSV权限不扩散            |
| 退订         | 必须双向同步，还要处理外部的整站退订与主题退订                            | 直接复用本地主题退订；发送前复查，退订可取消尚未发出的任务        |
| 防重复与排队 | 平台处理分发；华伴仍需活动登记、同步去重及不确定提交的核对                | 华伴开发逐人唯一键、并发抢占、重试、暂停与额度控制                |
| 发送结果     | 外部提供结果视图；回到华伴仍需接收事件                                    | 华伴只显示可靠的排队、已提交、收件服务器已接收、失败/退信等状态   |
| 运营负担     | 多一个后台，邮件编辑省力；需管理员负责两边名单一致                        | 一套中文后台；遇到异常队列、回执或额度问题更依赖开发维护          |
| 主要风险     | 同步延迟、外部手动改名单或稿件、外部账号越权                              | 自建发送逻辑的正确性、运维和投递异常处理                          |
| 开发量粗估   | 约 4–7 个工程工作日，含双向同步、回执及本地模拟；不含账户实测             | 约 6–10 个工程工作日，约 4–6 个小 PR；不含账户实测                |

以上是基于当前代码的规划估算，不是交付日期承诺。A 的高级营销分析依套餐，不能把所有报表都算作免费能力。两案都使用 Resend 承担实际邮件投递，**B 也会把收件邮箱和正文交给供应商，并非数据完全不出华伴**。两案均须核实供应商日志与退订凭证处理，默认不开启打开/点击跟踪。

Resend 的 Broadcasts 提供编辑、分组、主题退订、排队和排期；名单同步、华伴权限和业务审计仍需自行衔接。 [官方 Broadcasts 能力](https://resend.com/docs/dashboard/broadcasts/introduction)

## 5. A 的落地方式及边界（仅方案）

1. 华伴双确认成功后才同步当前有效订阅；待确认、已退订、测试库数据不得加入可发名单。同步最小字段为邮箱、语言、主题和内部同步标识，不上传国籍、入境日期、咨询、报价、来源路径、合作方编号或确认凭证。
2. 用两个语言 Segment 与政策更新 Topic 区分受众；Topic 必须采用“未显式订阅则不接收”的行为，并用实际测试证明，不能只凭界面里 Opt-in/Opt-out 字样判断。群发须同时限定正确语言分组和 Topic。单场展会等未来要单独映射，不能自动加入。
3. 华伴同意记录是加入/重新加入的依据；**任一侧的退订或拒发优先**。本地退订先立即停止本地任务，再同步外部；外部主题退订回写对应主题，外部全局退订作为额外全营销拒发状态。无新一轮明确同意，不得被历史同步重新订上；一次主题重订也不能顺便恢复其他主题。
4. 回调需验签、按事件 ID 去重、处理乱序及版本，再做定期对账；不能用一条迟到的“已订阅”事件覆盖较新的退订。外部有消息不确定、同步积压或对账失败时暂停该受众的群发。官方区分全局退订和 Topic 退订，二者不能互相替代。 [主题偏好](https://resend.com/docs/dashboard/contacts/manage-topics) [全局退订](https://resend.com/docs/dashboard/contacts/managing-unsubscribe-list)
5. 正式发前完成名单/退订同步，记录本次内容版本、目标、人数、外部 Broadcast ID、操作者和结果。平台开始分发后存在退订与发送的时间竞争，不能承诺撤回已投递邮件。
6. 外部控制台默认只给管理员使用；若平台权限不能限制名单读取，就不给普通主管开外部账号。华伴可记录主管确认，但外部用户仍可能修改稿件或绕过华伴入口发送，**本方案 A 不能保证华伴中的确认条件被外部控制台强制执行**。若要求所有发送都由华伴强制把关，需改为 API 控制的另行设计，不能假称这里的 A 已具备。
7. 断网/超时不能盲目再建一份 Broadcast；保留外部 ID，先核对状态。官方目前的幂等键文档列出的是 `/emails` 等接口，不能直接推定创建/发送 Broadcast 也有同样保护。中止后从原活动恢复，不另建同内容活动重发。

## 6. B 的建议默认规则（全部待用户确认）

### 6.1 权限和运营流程

- 管理员向主管单独授予指定主题的群发操作权限，默认无人获此新权限；主管看到汇总人数和发送状态，不因此取得订阅邮箱列表或 CSV 权限。普通运营不能发群发、不能通过接口绕过。管理员原名单管理权保持不变。
- 首批只选已发布的政策版本，按其来源、核实日期和中英文事实生成模板。内容/事实仍走原审核发布规则；不从草稿、内部备注或未核实资料生成正文，也不在群发页改事实。
- 流程：创建草稿 → 选择政策和主题 → 中英文预览与人数 → 测试 → 已授权主管手动确认发送 → 查看逐人汇总 → 暂停/取消未发任务。既定停止点要求主管与测试，本建议**不额外默认新增群发二审制度**；同一主管可以测试后手动确认。报价、内容的二审规则不因此改变。
- 本地“测试”只生成模拟邮件，界面明确标为模拟、未实际送达。未来真实发前必须向管理员配置的内部测试收件人发测试并由主管确认可读；账号配置齐备不算测试通过。测试结论绑定内容、来源版本、发件配置及语言，相关内容变化后失效。
- 发送确认冻结本轮内容、主题、语言版本、收件资格快照、预计人数及操作者。每批一个主题；同一邮箱在同一批只收一封，按该主题的有效同意语言发送，缺语言版本则排除并提示，不擅自换语言。确认后的新增订阅不补入旧批次。
- 每次发送前重读当前订阅状态和同意版本；排除退订、失效同意、拒发名单及撤权的操作者。原政策版本被修改、下架或不再有效时暂停尚未发出的任务，重新生成并测试后才能再确认；已投递内容不能撤回。
- 建议政策改版后**保留原活动 ID，仅续发从未尝试发送的剩余收件人**。已由供应商接受、已送达或结果待核对者不重新入队，已尝试的旧正文/唯一键不改写。若需给已收件人发送更正，必须另建明确标注原活动及更正内容的活动，重新测试和手动确认，不自动补发，也不绕过频控。

### 6.2 防重复、限额、退订及投递回执

- 新建独立营销活动/逐人任务和回执记录，不把大名单塞入现有单封确认队列。任务保存订阅 ID、同意版本、活动版本及状态；不额外复制整份联系人库。按“稳定活动 ID＋规范化邮箱摘要”建立跨版本唯一收件标识，同意或内容版本变更都不能让同一活动再收一次。首次尝试前冻结正文和该任务的唯一键。
- 沿用现有邮件适配器和工作流 worker 的部署方式，但新发送资格与额度需专门实现和测试。单封请求、逐人持久唯一键、任务抢占与租约；多个进程共用数据库额度，不能每个 worker 都各发一份。发件前的退订/权限复核与任务占用必须处理并发，不能只在生成名单时判断。
- 首批建议限制：每批最多 1,000 人，全部营销批次合计每天最多 2,000 封（北京时间）；同邮箱滚动 24 小时最多 1 封营销邮件。全站发件调度先保守按每秒 1 次请求，并适应实际供应商额度及 429 的 Retry-After，人工配置不会覆盖平台上限。
- “1 封营销”按已占用的唯一营销任务计算，结果不明也占位；同键重试不算新一封，但每次传输尝试都计入共用的 5 次尝试预算。不得通过重建活动或换键绕过额度。
- 这一频控意味着同一邮箱的同日多项变化应合并成一封，更正活动也可能需等到限额释放。若运营要求同日紧急追加或纠错通知，需用户另行明确例外规则；不得伪装成用户主动请求绕过频控。
- 现有确认/资料的跨主题 15 分钟及滚动 24 小时 5 次尝试上限继续成立；新营销尝试也纳入同邮箱共用计数，另受上面的 1 封营销上限限制。营销退让确认/资料邮件。全站账单预算还要为确认、报价等业务邮件预留；账户共享用量、余额不清楚或额度不足时暂停营销，绝不为了发群发放宽旧限额或自动付费。
- 重试沿用同一正文、同一唯一键，最多 5 次；从第一次尝试算起最多 23 小时，超出窗口或结果不明则停为“待核对”，不自动换键再发。因为供应商幂等保留 24 小时，不能许诺跨无限时间的绝对只发一次。429/暂时失败排队退避，永久退信/投诉立即拒发，不自动重试。
- 每封邮件生成本轮有效同意版本的退订凭证，复用网页退订与邮箱客户端一键退订；不沿用早已过期的确认邮件链接。退订只影响所选主题并取消对应未发任务；再订阅必须新双确认，不复活旧活动。每个收件人单独发件，不用 To/CC 暴露其他邮箱。
- 接收经签名验证的送达、退信、投诉及抑制事件，重复回调不重复处理，迟到的成功不能覆盖投诉/退信。硬退信或投诉进入独立营销拒发状态，保留同意历史，不能由一次普通重订自动清除。关闭群发不关闭退订和必要的投递回执入口。
- “供应商已接受请求”和“收件服务器已接收”分开记录，均不宣称用户已经阅读。默认不做个人打开/点击跟踪。名单及逐人失败详情仍仅管理员可见；主管只看授权活动的汇总。操作和审计不保存原始凭证，正文与供应商日志的凭证风险沿用既有上线门禁。

供应商仅负责邮件传输，华伴仍需实现并发、预算、暂停与拒发管理。官方 API 按团队限速；重试幂等、事件类型和原始正文验签要求应在实施时再次核对。 [API 限速](https://resend.com/docs/api-reference/introduction) [幂等键](https://resend.com/docs/dashboard/emails/idempotency-keys) [投递事件](https://resend.com/docs/webhooks/event-types) [验签](https://resend.com/docs/webhooks/verify-webhooks-requests)

## 7. 批准之后如何分批，而不提前外发

选择 B 后建议按顺序拆 4–6 个小 PR，每个合并后再开下一个：活动/权限/版本和预览；本地模拟测试及确认条件；逐人调度/额度/防重复；退订竞争/暂停/回执拒发；最后做整链路验收。单批业务改动超过 400 行继续拆。选择 A 则改为：模型映射与模拟同步；退订双向同步和对账；活动记录与外部操作核对；整链路模拟验收。

两案均先用虚构资料、模拟 API/邮件与签名事件完成测试：匿名/运营/撤权拒绝，未确认不加入，错误语言和过期内容拦截，多 worker 不重复，超时/429/进程中断，退订与发件竞争，新同意不复活旧任务，伪造/重复/乱序回执，测试稿变化失效，额度不足/审计失败不外发。A 另测同步积压、外部全局/主题退订、手动名单差异及对账；B 另测共同邮箱限额、跨日预算、逐人唯一键和内容改版只续发未尝试者、更正不自动重发。只写方案的本 PR 不声称这些尚未实现的测试通过。
